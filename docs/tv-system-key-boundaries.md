# MateTV 系统按键的接收边界

2026-10-25。本记录依据本机 DevEco SDK、现有输入测试页和实机反馈；不代表新增按键已通过电视验收。

## 能确认的接口

本机 SDK 根目录为 `/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/ets`。

| 接口或键值 | SDK 依据 | 对屏间的意义 |
| --- | --- | --- |
| `KEYCODE_MENU = 2067` | `api/@ohos.multimodalInput.keyCode.d.ts:646` | 可以处理实际到达应用的菜单事件；不能据此保证遥控器会发送。 |
| `KEYCODE_SEARCH = 9` | 同文件第 61 行，API 13 | 搜索键候选，不等同于已确认的实体语音键。 |
| `KEYCODE_ASSISTANT = 2722` | 同文件第 1990 行，API 9，注释 Smart key | 助手键候选，仍需实际事件配对和设备绑定。 |
| `onKeyEvent` | `component/common.d.ts:18643`、18656 | 接收焦点组件的按键；API 15 的布尔返回值表示是否处理。 |
| `onKeyPreIme` | 同文件第 18687 行，API 12 | 焦点组件内先于输入法和其他按键回调；返回 `true` 会截断后续处理。它不承诺绕过系统助手。 |
| `onKeyEventDispatch` | 同文件第 18704 行，API 15 | 处理组件已收到的事件，不支持凭空创建按键并分发。 |

以上 ArkUI 接口没有声明敏感权限。SDK 中有 `KEYCODE_VOICEMAIL = 2708`，其含义为语音信箱，不能当作电视听写键。

`inputConsumer.on('keyPressed')` 也不是任意系统键拦截接口。`api/@ohos.multimodalInput.inputConsumer.d.ts` 的 `KeyPressedConfig.key` 明确列出：API 20 及以前仅音量加减，API 21 增加媒体播放/暂停和上一曲/下一曲；更高版本另有指纹滑动键。没有列出菜单、助手或搜索键。全局组合键接口要求修饰键，且系统占用会报错，同样不是接管小艺的方案。当前普通应用 `window` API 没有检索到任意原始按键订阅入口。

## 实机证据与不足

用户已经确认：系统键盘显示时，长按遥控器语音键能听写进输入框；键盘收起后，同一操作唤起小艺。该结果证明系统会依上下文路由语音操作，但不能证明屏间拿到了这个键的原始 Down/Up。

现有 `TvInputLab.ets` 使用可聚焦测试区域的 `onKeyEvent`，只在页面展示键值和类型；没有记录设备 ID，也没有 PreIme 对照。抽查现有语音与输入日志时，框架部分键值为 `<private>`。目前未找到可归因于实体语音键或菜单键的完整候选键 Down/Up 记录；不能把“日志未找到”写成“固件绝不支持”。

## 最少实机测试

1. 先用方向键确认焦点、事件通道和遥控器绑定正常。测试时不要连接蓝牙键盘触发同名候选键。
2. 系统键盘隐藏，聚焦学习按钮；按菜单键一次，再短按、长按语音键各一次。只记录事件时间、接收阶段、`keyCode`、`deviceId`、Down/Up、当前前后台/焦点状态。不要记录输入正文。
3. 仅当同一绑定设备实际收到允许的候选键完整 Down/Up 后，才允许用户确认映射。长按产生重复 Down 不能当作双击；后台、失焦或超时必须取消未完成学习。
4. 若只唤起小艺而学习入口无事件，先以方向键再次证明焦点有效。必要时在诊断构建为同一焦点组件加只读 `onKeyPreIme` 日志并返回 `false`，排除应用内输入法先消费；不要同时在两个阶段执行映射。
5. 再以键盘显示时的语音听写作为对照。不能为了抢语音键在所有 PreIme 事件返回 `true`，否则会破坏正常输入与返回键。

学习成功也仅适用于已验证的固件和输入设备。若系统不给应用事件，保留麦克风按钮和系统键盘听写，不通过系统应用权限或全局拦截尝试绕过。此限制位于电视的系统输入路由，尚无证据指向 RustDesk 协议或电脑端；修改电脑端 RustDesk 无法产生电视没有送达的原始按键。
