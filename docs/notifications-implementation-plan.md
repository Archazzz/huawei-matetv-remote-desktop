## 首版交付范围

用户希望看原生视频应用时也收到通知，因此「仅屏间前台可见」只能作为开发原型，不能代表需求完成。

1. **前台闭环**：配对电脑提交通知，屏间展示来源电脑、来源软件、标题和正文，点击连接对应电脑；支持收件箱查看完整文字。
2. **后台闭环**：屏间不在前台甚至进程未运行时，由华为 Push Kit 通知消息展示系统提醒，点击启动屏间并消费同一个通知路由。
3. **真实来源**：首批 Codex 和普通微信，各自明确采集方法与实际覆盖范围。可手工提交通知的命令行接口只验证通道，不算自动同步完成。

系统横幅的长度、位置、持续时间由电视系统决定。完整长正文在屏间内保留，不承诺系统横幅无截断。系统发布者为屏间，内容中标识来源，不能伪装为微信或 Codex 自己的系统通知。

## 电脑采集入口

### Codex 桌面版

官方 `openai/codex` 的 hooks 源码确认 `Stop` 输入含 `session_id`、`turn_id`、`last_assistant_message`，可直接转发完成回复。公开项目 Seacolour/CodexHookNotify 明确提供桌面版 Stop hook 接法；本机 bundled CLI 0.163.0-alpha.11 的 `features list` 显示 `hooks stable true`。采用独立原创适配器，不需要读取聊天库或辅助功能权限。本机已安装并信任，用户已确认真实 Mac Desktop 完成事件送达。

`PermissionRequest` 在 guardian／用户审批 UI 之前触发，因此只表示发生权限请求，不能声称用户此刻仍需批准。`request_user_input` 相关 hook 是否在当前桌面运行还需实测，不以问号或工具参数启发式猜测。

本机已有 `notify` 配置用于电脑操作工具，保留不覆盖。新增配置使用 `hooks.json`，合并而不替换其他 hook；执行器保持 stdout 为空、退出 0，不向审批系统返回 allow／deny。只传最终回复，不传 prompt、cwd 或 transcript 路径。最终回复与系统通知横幅不是同一文本来源，应在交付中明确说明。

参考：[官方 Stop](https://github.com/openai/codex/blob/main/codex-rs/hooks/src/events/stop.rs)、[官方 PermissionRequest](https://github.com/openai/codex/blob/main/codex-rs/hooks/src/events/permission_request.rs)、[CodexHookNotify](https://github.com/Seacolour/CodexHookNotify)。

### 普通微信

已实现独立 Mac 助手，通过只读系统通知库监听启动之后的新微信通知。启动时仅读取结构与最大行号，不读取历史正文；只选择系统来源标识精确匹配微信的新记录，不读取微信聊天库、联系人或会话历史。数据库替换或水位倒退重新建立基线，不补传历史。聚合通知的原记录更新目前不转发。

本机访问系统通知库受到 TCC 拒绝，需要仅给独立助手“完全磁盘访问”权限；不要求扩大 Codex 或终端权限。助手已构建，尚未授权或启动。用户没有第二个微信账号，不要求继续自发消息测试，授权后等待自然出现的真实系统通知验收。

原文模式同步系统记录的标题、副标题和正文，并标记 `unknown` 或 `truncated`，不会将数据库原文冒充已经验证的横幅可见内容。系统隐藏预览是否准确反映在该记录中尚需验证。也支持不读取正文的隐藏模式。详见 [微信监听器说明](../mac-assistant/wechat-listener.md)。辅助功能结构探测保留为诊断工具，不将其宣称为已成功采集微信。

日志仅记录状态、计数和长度，不输出正文或联系人。独立助手有开始、停止入口，未设置开机自启。

## 消息协议与电脑映射

建议独立通知服务，避免修改现有 RustDesk 转发服务的协议和可用性。通知事件字段如下：

| 字段 | 语义 |
| --- | --- |
| `version`、`eventId` | 协议版本和幂等标识 |
| `deviceId` | 配对电脑身份，由服务端凭据绑定，拒绝正文伪报身份 |
| `appId`、`appName` | 已允许的软件来源；无法可靠识别来源则不转发 |
| `title`、`body` | 系统暴露的原文；展示转义，不作为 HTML 或指令执行 |
| `createdAt`、`expiresAt` | 时间与期限；离线补发丢弃过期事件 |
| `captureMethod`、`contentState` | 原始事件/辅助功能来源，以及完整/截断/隐藏预览状态；不能将未知标成完整 |

使用独立配对凭据、TLS 和有限保留期。Tailscale 保护已有跨网段通道，但不能代替应用级设备身份验证。日志不记正文、配对密钥或远控密码；配对配置保存在忽略的本地目录。

同一 MacBook 的局域网卡片和 Tailscale 卡片属于同一个 `deviceId`。首次绑定时选择一张现有卡片作为默认连接目标，不按通知内的 IP 临时创建连接，也不自动把同一条消息发成两个电脑来源。后续允许更改默认卡片。

前台消息和后台推送复用 `eventId` 去重。推送包含受限事件标识与来源映射，不放远控凭据、任意 host 地址或命令。华为通知消息如果携带正文，正文会经过华为推送服务；这是后台方案的数据路径，不能称为纯局域网方案。

## 点击路由与会话生命周期

1. EntryAbility 在冷启动或 `onNewWant` 收到点击后，只把事件标识交给通知协调器，不立即打开远控页面。
2. 协调器等待账户、本机存储和主窗口初始化；验证事件有效、来源配对仍存在、目标 `hostId` 属于当前作用域。
3. 当前已连接同一目标时，只恢复现有页面；未连接时复用保存的认证与连接流程。
4. 当前连接其他目标时，取消当前按键/拖动状态，按现有串行断开路径等待原生终态，再连接新目标。不能用超时直接清除单会话占用。
5. 重复点击只保留同一个待处理目标；明确的更新点击可替代尚未执行的目标，避免排队连接多台电脑。
6. 电脑已删除、凭据丢失、事件过期或断开失败时，停留在可解释的收件箱/电脑列表，不绕过认证或卡死遥控输入。

通知到达只展示，不主动切换当前远控电脑。只有用户点击才切换。

## 后台系统通知的前置条件

需要核验应用在 AGC 的 Push Kit 开通、签名对应关系、Token 取得、通知授权和服务与通讯消息类别权益。现有调试签名不能自动证明这些条件已满足。实际是否在电视播放其他应用视频时弹横幅、点击后的冷/热启动行为，必须在当前 TV 实测。

普通后台 WebSocket 可能随挂起或终止停止。不能借播放静音音频、伪造数据传输任务或保活循环来冒充可靠推送。若 Push Kit 条件暂不具备，可以交付前台原型并明确缺少后台功能，不能声称完整通知同步已完成。

## 可自主实施与实机门槛

可先完成事件验证、幂等/过期处理、来源映射、认证中转、前台收件箱与点击协调器，并用纯样例测试；这些工作不需要先读真实聊天。可准备 Mac 助手项目与独立权限引导，但不把编译成功当作采集成功。

需要实机验证的门槛：

- Codex Stop hook 在 Mac Desktop 真正触发并送达；微信通知来源能否可信识别、正文是否完整，覆盖中文、长文、隐藏预览、更新与聚合。
- 当前 TV 前台/其他视频应用前台/屏间进程未运行三种状态的到达、横幅、点击与认证行为。
- 正在远控时点击另一台电脑的通知，旧会话释放完成后才能进入新电脑；重复点击不制造并发会话。
- MacBook 经 Tailscale 发送到中转再到 TV；断线重连不重复弹出过期通知。
- 关闭来源、解除配对、清除通知历史与撤回权限后，不继续转发。

只有真实来源、后台到达和点击直达均实测通过，才把该来源标记为已支持。每个来源分别报告结果，不以一条合成通知的成功替代全部验收。
