# 电视音频延迟与电脑同播核查

核查日期：2026-10-25。本轮只读源码、SDK 和已有诊断日志，没有修改 native 音频策略、切换系统输出或播放测试声音。以下历史日志不能代表后续新版本的当前性能。

## 结论

当前电视音频链路主动保留较大的抖动缓冲，足以解释电脑音响先响、电视随后响的一部分延迟。提高视频码率不能消除这段音频排队。用户目前认为电视内音画同步，但视频不够流畅；因此不应在未联测视频延迟时单独把音频缓冲压低，否则可能使声音领先画面。

电脑和电视精确同播还需要共同时间基准，以及把较早发声的一端延后。现有 RustDesk 音频回调没有保留源时间戳，无法仅靠电视端参数保证两端无回声。低延迟远控、电视内音画同步、电脑与电视多端同播是三个分别需要测量的目标。

## 20ms 回调的 SDK 可用性

核查本机 DevEco SDK 的 `native/sysroot/usr/include/ohaudio/` 头文件：

| API 和行号 | SDK 声明 | 如何验证 |
| --- | --- | --- |
| `native_audiostreambuilder.h:354`，`OH_AudioStreamBuilder_SetFrameSizeInCallback` | API 11 起可用；帧数至少为设备单次处理量，并且小于内部缓冲容量的一半 | 48kHz 下请求 960 帧是 20ms；创建前调用，记录返回码，不能仅凭函数成功认定实际 20ms |
| `native_audiorenderer.h:295`，`OH_AudioRenderer_GetFrameSizeInCallback` | API 10 起可用 | 创建后读取实际帧数，同时记录实际 callback 字节数，核对是否被调整 |
| `native_audiorenderer.h:280`，`OH_AudioRenderer_GetTimestamp` | API 10 起可用，CLOCK_MONOTONIC，纳秒时间戳；不适应播放速度变化 | 可作旧版本播放进度观测；刷新/路由切换后需重新建立基准 |
| `native_audiorenderer.h:575`，`OH_AudioRenderer_GetAudioTimestampInfo` | API 15 起可用，适应播放速度变化；位置是刚提交硬件的帧，flush/路由切换时可能重置 | 优先测量播放位置，稳定后再用来估算系统队列；不是声波实际抵达听众的时间 |
| `native_audiorenderer.h:715`，`OH_AudioRenderer_GetLatency` | API 23 起可用；仅给路由延迟估计，不包括实时缓冲状态；不应频繁查询 | 必须确认 TV 运行时 API 后再用，不能按 SDK 编译成功假定设备支持 |

设备当前“17832 字节”的 NORMAL 回调，不能证明请求 960 帧一定被接受。SDK 没要求该接口只能在 FAST 下调用，但真实路由最小处理粒度可能限制结果。即便实际回调缩到 20ms，内部输出缓冲也不必然等量缩小。优先保持 NORMAL 做受控对照；直接换 FAST 可能增加回调频率与 CPU 争用，不能作为无代价优化。

## 后续可验证方案

1. 固定本地 60fps 素材、电脑显示器、实际编码器和电视显示模式，先记录接收/解码/显示帧率及帧间隔，确认视频问题所在。不要同时调码率、帧率和音频缓冲。
2. 在现有策略下采集 PCM 队列毫秒的中位/P95、Opus 入队到解码年龄、实际 callback 帧数、underrun/丢样本增量，以及 OHAudio 播放位置；诊断只记数值，不录制声音内容。
3. 在可切回原策略的实验分支，先请求 960 帧/20ms callback，保持原预缓冲；比较实际块大小、CPU、underrun 与音画同步。请求失败或实际块大小未变时保留原配置。
4. 若前项稳定，再试局域网 40–60ms 预缓冲目标，并设置有界的积压恢复策略。减小缓冲是实验目标，不是已验证参数。持续积压应渐进恢复，不能任意丢掉大段 PCM 导致爆音；外网需要独立保留较大抖动预算。
5. 与同一音画测试素材联测。若音频明显领先视频，先减少视频排队/解码负载，或基于测得的时间线安排播放，不能因为声音快了就认定体验改善。
6. 验证切显示器、前后台、路线变化、丢包恢复和重新连接，确保旧会话缓冲不复用。明确记录已构建、已安装和听感/测量结果。

## 电脑与电视同时播放的边界

现在电脑播放路径先到真实输出端点，远控再采集并传至电视。电视无法播放尚未抵达的数据，通常是更晚的一端。要听起来对齐，需要把电脑实际出声延后到共同播放时刻，同时保持采集发生在该延迟之前。

仅在播放器中设置音频延迟通常会一起推迟电脑输出和被采集内容，电视仍在其后；不能消除两端差值。现有端点静音控制能切成电视独占发声，但不是多端时间同步。精确同播需要电脑助手提供分离的采集/输出、双方时钟映射、时间戳、漂移控制和目标播放缓冲；可能涉及应用专用输出或虚拟路由，但本轮没有证明必须安装某个虚拟声卡，也没有安装。

即使网络极好，输出设备与两个房间的声程也不同。应先约定可接受的时间差并用受控样例测量，不承诺“零延迟”。现阶段更小的电视缓冲与电脑静音/电视独占可以分别推进；精确双端同播应作为独立功能设计。
